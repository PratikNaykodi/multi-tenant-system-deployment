Multi-Tenant System – Production Deployment Guide
React + Node.js + Express + Prisma + PostgreSQL + Socket.IO + Render + Namecheap
Step 1: Create PostgreSQL Database on Render
•	Open Render Dashboard → New → PostgreSQL.
•	Create the database with database name: multitenant_central.
•	Keep PostgreSQL and the backend in the same Render region when possible.
•	Save the Host, Port, Database, Username, and Password.
•	Never commit the database password to GitHub.
Step 2: Connect PostgreSQL Using DBeaver
•	Open DBeaver and create a PostgreSQL connection.
•	Host: use the Render PostgreSQL host.
•	Port: 5432.
•	Database: multitenant_central.
•	Username: use the Render PostgreSQL username.
•	Password: use the Render PostgreSQL password.
•	Click Test Connection and confirm it succeeds.
Step 3: Configure Prisma
•	Open the backend project.
•	Make sure Prisma is configured for PostgreSQL.
•	Configure DATABASE_URL and CENTRAL_DATABASE_URL.
•	Run locally: npx prisma validate
•	Run: npx prisma generate
•	Run: npx prisma migrate dev
•	Confirm that the central database tables are created.
Step 4: Push Prisma Migration to GitHub
•	Run git status.
•	Add the Prisma schema and migration files.
•	Commit the changes.
•	Push to the main branch.
•	Render will run prisma migrate deploy during backend deployment.
Step 5: Deploy Backend on Render
•	Render → New → Web Service.
•	Connect the GitHub repository.
•	Branch: main.
•	Root Directory: backend.
•	Runtime: Node.
•	Build Command: npm install && npx prisma generate && npx prisma migrate deploy
•	Start Command: npm start.
•	Create the Web Service.
Step 6: Configure Backend Environment Variables
•	PORT=10000
•	DATABASE_URL=<Render PostgreSQL connection URL>
•	CENTRAL_DATABASE_URL=<same central PostgreSQL connection URL>
•	PG_HOST=<Render PostgreSQL host>
•	PG_PORT=5432
•	PG_USER=<PostgreSQL user>
•	PG_PASSWORD=<PostgreSQL password>
•	JWT_SECRET=<strong secret>
•	ENCRYPTION_KEY=<64-character hexadecimal key>
•	ALLOWED_ORIGINS=<frontend origins>
•	Never commit these values to GitHub.
Step 7: Test Backend
•	Open the Render backend URL.
•	Expected response: {"message":"Multi-Tenant API is running"}
•	Test POST /api/tenants with a clinic name and domain.
•	Confirm that the response contains the tenant identifier and database name.
Step 8: Deploy React Frontend on Render
•	Render → New → Static Site.
•	Connect the GitHub repository.
•	Branch: main.
•	Root Directory: frontend.
•	Build Command: npm install && npm run build
•	Publish Directory: dist.
•	Create the Static Site.
Step 9: Configure Frontend Environment Variables
•	VITE_API_BASE_URL=https://<backend-domain>/api
•	VITE_SOCKET_URL=https://<backend-domain>
•	Vite embeds environment variables during build, so redeploy after changing them.
Step 10: Configure the Main Domain
•	In Render frontend → Settings → Custom Domains, add mytenantdemo.site.
•	In Namecheap Advanced DNS, configure the DNS records supplied by Render.
•	Wait until Render shows the domain as verified and SSL as issued.
•	Test https://mytenantdemo.site.
Step 11: Configure Wildcard Tenant Domain
•	Add *.mytenantdemo.site in Render.
•	Render may require CNAME * → multi-tenant-system-deployment.onrender.com.
•	Render may also require _acme-challenge → multi-tenant-system-deployment.verify.renderdns.com.
•	Render may also require _cf-custom-hostname → multi-tenant-system-deployment.hostname.renderdns.com.
•	Enter only the host values (*, _acme-challenge, _cf-custom-hostname) in Namecheap.
•	Wait until Render shows Verified and Certificate Issued.
Step 12: Configure Tenant URL
•	For Boston Clinics with identifier bb, the production URL should be https://bb.mytenantdemo.site.
•	The frontend should generate the production URL instead of http://bb.local:5173.
Step 13: Tenant Detection
•	When https://bb.mytenantdemo.site is opened, the application should identify bb.
•	The backend should locate bb in the central database and connect to tenant_bb.
•	For production security, validate the tenant from the hostname instead of trusting only x-tenant-id.
Step 14: Configure Production CORS and Socket.IO
•	Allow https://mytenantdemo.site and https://www.mytenantdemo.site.
•	Allow tenant subdomains such as https://bb.mytenantdemo.site.
•	Use dynamic origin validation for tenant subdomains instead of a literal wildcard CORS origin.
•	Socket.IO must use the production backend URL and allow tenant frontend origins.
Step 15: Test Login
•	Open https://bb.mytenantdemo.site.
•	Login with the tenant admin account.
•	Confirm login, JWT handling, tenant identification, API calls, and dashboard loading.
Step 16: Test Tenant Isolation
•	Create ABC Company → tenant_abc.
•	Create Boston Clinics → tenant_bb.
•	Open https://abc.mytenantdemo.site and https://bb.mytenantdemo.site.
•	Confirm that each tenant can access only its own database and data.
Step 17: Test Socket.IO Appointment Updates
•	Login as a provider in one browser.
•	Login as a patient in another browser.
•	Create an appointment as the patient.
•	Confirm the backend saves it and emits the Socket.IO event.
•	Confirm the provider appointment list updates automatically without a manual reload.
Step 18: Final Production Checklist
•	PostgreSQL: central database created, DBeaver tested, Prisma migrations deployed.
•	Backend: Render deployed, environment variables configured, health URL works, CORS and tenant middleware configured, Socket.IO configured.
•	Frontend: Render deployed, API and Socket.IO URLs configured, production build succeeds.
•	Domain: root domain verified, SSL issued, wildcard domain verified, wildcard SSL issued.
•	Tenant: tenant creation works, tenant database is created, production URL is generated, login works, isolation is verified, appointment Socket.IO update works.
